# YuCap — キャプチャビューア

USB キャプチャボード（UVC/UAC 準拠。想定機種：j5create JVA14）の映像・音声を
**「見るだけ＋スナップショット」**に特化した Windows デスクトップアプリです。録画機能は持ちません。

Media Foundation の Capture Engine を使い、プレビューを **GPU で直接ウィンドウへ描画**します。
NV12/P010 をネイティブに扱えるため、DirectShow では届かなかった **1080p120 / 1440p60 / 4K30** が使えます。

## 動作環境

- Windows 10 / 11（x64）
- [.NET 8 デスクトップランタイム](https://dotnet.microsoft.com/download/dotnet/8.0)
- UVC/UAC 準拠の USB キャプチャデバイス

動作確認済み: j5create JVA14（1080p120 NV12）、Windows 11

## インストール

[Releases](https://github.com/Yu5rin/YuCap/releases/latest) から `YuCap.exe` をダウンロードして任意の場所に置くだけです（インストーラ不要）。
設定は `%APPDATA%\YuCap\settings.json` に保存されます。

## 更新

起動時に新しい版を確認し、あれば裏でダウンロードして照合します。視聴は中断されません。
準備ができると画面に通知が出て、**YuCap を閉じたときに置き換わります**（通知のクリックや
**ヘルプ → 再起動して更新** で、その場で再起動して更新することもできます）。閉じ損ねた場合
（強制終了など）は、次回起動時に新しい版へ置き換えてから起動します。
**オプション → 自動で更新する** でオフにでき、オフの間は何も入れません。
**ヘルプ → 更新を確認...** でいつでも手動で確認できます（詳しくは「外部通信について」を参照）。

照合用のハッシュが公開されていない版や、書き込めない場所に置いている場合は、自動では入れず
通知だけを出します。その場合は YuCap を終了してから Releases の新しい `YuCap.exe` で
置き換えてください。設定はそのまま引き継がれます。

## 主な機能

- **自動デバイス選択** — デバイス メニューで最後に選んだ映像・音声の機器を優先し、次に名前に指定キーワード（既定 `JVA14`）を含む機器を使います。どちらも見つからないときは別の機器（マイクやウェブカメラ）を勝手に開かず、「キャプチャーボードが見つかりません」と表示して、接続されるか手で選ぶのを待ちます（初回起動でキーワードに合う機器がないときも同じです）
- **抜き差し検出と自動再接続** — ケーブルを挿し直すと映像・音声が自動復帰。既定の再生デバイス変更にも追従します。映像や音声が途中で勝手に止まったときも、「つなぎ直しています」と表示して 1 秒・2 秒・5 秒の間隔で自動的にやり直し、それでも戻らないときは画面とステータスバーにそう表示します（抜き差しすると再開します）。スリープからの復帰後は、機器の認識が遅れても数秒間やり直します
- **表示モード** — アスペクト比保持／引き伸ばし／原寸／**整数倍**（ドット絵がボケない）
- **高画質拡大（試験版）** — 映像 → 描画方式で「Direct3D」を選ぶと、ウィンドウや全画面が入力より大きいときに
  AMD FidelityFX FSR 1 で拡大します（映像 → 拡大の画質、シャープさも調整可能）。1440p 入力を 4K で見るときなどに効果があります。
  拡大の画質を「くっきり（アニメ・イラスト向け）」にすると、Anime4K のニューラルネット（CNN）で線や文字を細くくっきり描き直します（GPU を多く使います。新しい絵ごとに 1 回だけ実行します）
- **色のにじみを抑える** — 映像 → 拡大の画質 →「色のにじみを抑える」（既定オン）。キャプチャカードの映像（NV12）は、明るさは細かく、色は縦横とも半分の細かさしかありません。以前は色を単純に引き伸ばしていたため、赤い文字などの縁に色がにじんでいました。細かい明るさの動きから色の変わり目を推定して、色の境目をくっきりさせます（色は MPEG-2 の左寄せ配置として扱います）。なめらかなグラデーションは変わりません。1080p の変換で GPU を約 0.17 ms 余分に使います（4K 入力で約 0.7 ms）。テストモードの「色の境目」で、既知の絵（正解つき）に対する色の PSNR と境目の幅を測ります。Direct3D 描画のとき働きます
- **ぼやけを取ってから拡大（試験版）** — 映像 → 拡大の画質 →「ぼやけを取ってから拡大」（既定オフ）。FSR・くっきりで拡大する前に、Anime4K Restore（小）でぼやけを取ります。既知の絵では SSIM が上がります（FSR 0.938 → 0.953、くっきり 0.940 → 0.959）が、GPU を 1080p で約 0.6 ms 余分に使い、縁に輪が出やすくなるため既定はオフです。「元の細かさに合わせて拡大」が絵を縮めているときは使いません（縮める方が良い結果でした）
- **AI 拡大（NVIDIA RTX）** — 映像 → 拡大の画質 →「AI 拡大（NVIDIA RTX）」。NVIDIA の RTX ビデオ超解像（VSR）を、D3D11 のビデオプロセッサーの拡張（`VideoProcessorSetStreamExtension`、Chromium と同じ呼び出し）で使い、映像（向きや色の調整を終えた絵）を画面の大きさへ拡大してから、オーバーレイなどを重ねます。NVIDIA の GeForce RTX と、NVIDIA コントロールパネルの「ビデオ イメージ設定の調整 → RTX ビデオ強調 → Super Resolution」のオンが必要です（オフのままだと呼び出しは成功しても絵は変わらないので、テストモードが VSR あり / なしの差を測って「VSR が働いていません」と知らせます）。NVIDIA 以外の GPU や失敗したときは FSR になります。負荷が高いときの自動調整の対象で、FSR に下がります
- **HDR 表示** — 映像 → HDR 表示。Windows でそのモニターの HDR をオンにしているときだけ選べます（オフのときは灰色で、手順をツールチップに出します）。表示のスワップチェーンを HDR10（R10G10B10A2・PQ・BT.2020）に切り替え、SDR の絵を「HDR で表示（NVIDIA RTX）」＝ドライバーの RTX Video HDR（AI）、または「HDR で表示（簡易）」＝自前の逆トーンマップ（SDR の白を紙白 203 nits の基準に置き、明るい部分を広げて白をおよそ 600 nits へ。オーバーレイ・OSD は紙白のまま）で変換します。静止画の保存は SDR のままです。RTX Video HDR が使えないときは簡易になります。オフのときは従来の SDR の経路と変わりません
- **負荷が高いときの自動調整** — GPU 時間が更新 1 回の 85% を約 2 秒超えると、くっきり（M）→ くっきり（S）→ FSR の順に軽くし（ぼやけ取りがオンなら先に止めます）、60% を下回る状態が約 10 秒続くと 1 段ずつ戻します。フレーム補間は止めません。設定は書き換えません。働いている間は、状態バーの映像欄のツールチップと情報表示に「負荷が高いため くっきり を軽くしています」と出ます（設定を変えた直後だけ OSD にも出します）
- **フレーム補間（試験版）** — 映像 → フレーム補間をオンにすると、モニターの更新が映像のコマ数より十分速いとき
  （例: 30 fps の映像を 60 Hz で、60 fps を 144 Hz で、120 fps を 144 Hz で見るとき）に、前後のコマの動きを調べて間のコマを作り、
  更新のたびに新しい絵を出して動きをなめらかにします。モニターの更新が映像のコマ数の 1.1 倍に届かないとき（60 fps の映像と 60 Hz など）や
  低遅延モードのときは自動で働かず、そのままの表示になります。働いているかは情報表示（Ctrl+Shift+I で「詳しく」）の「補間」で分かります。
  間のコマを作るために、映像が 1 コマぶん遅れます（30 fps なら約 33 ms）。素早い動きや、物の陰から何かが現れる場面では絵が乱れることがあります
  （Direct3D 描画のとき。初期設定はオフ）
- **映像の調整** — 映像 → 映像の調整で、明るさ・コントラスト・彩度・ガンマを動かしながら確認できます。保存するスナップショットにも反映されます（Direct3D 描画のとき）
- **暗部補正** — 映像 → 暗部補正（または映像の調整）で、暗い場面の暗い部分だけを持ち上げて見やすくします。オフ／弱／中／強の4段階で、明るい部分と真っ黒はそのままです（色味も保たれます）。スナップショットにも反映されます（Direct3D 描画のとき）。プロファイルごとに覚えます
- **音ズレ補正** — 音声 → 音ズレ補正で、映像と音のずれを ±300ms の範囲で合わせます。音を早める側は映像を遅らせて合わせるため Direct3D 描画のときに使えます。画面には「いまの遅れ」（映像と音が YuCap と Windows の中で何 ms かかっているか）がリアルタイムで出て、［目安に合わせる］で差がなくなる位置に動かせます
- **音ズレの自動補正** — 音ズレ補正の画面で「自動で合わせる」を入れると、映像と音の「YuCap の中の遅れ」の差を測りながら、少しずつ自動で合わせ続けます（Direct3D 描画のとき。標準の描画では映像の遅れを測れないため使えません）。キャプチャボードやテレビ・スピーカーの中の遅れは測れないので、その分はスライダーの「微調整」で足してください（自動の補正量＋微調整が実際の補正量になります）。補正は数秒の測定のうえで 1 回数ミリ秒ずつで、音は途切れさせずに延ばし縮みさせます。画面には「音ズレ 自動」と出ます。プロファイルごとに覚えます
- **遅延の表示** — 情報表示（Ctrl+Shift+I で「詳しく」）の「遅延（YuCap 内）」、音ズレ補正の画面、テストレポートに、映像と音が「キャプチャボードから YuCap に届いてから、画面に出る・音が鳴るまで」にかかる時間を出します（映像は Direct3D 描画のとき）。キャプチャボードやテレビの中で生じる遅れは測れないため含まれません。目安として使ってください
- **プロファイル** — 接続元ごと（Switch 2 と PC など）に、映像モード・描画方式・拡大の画質・フレーム補間・表示モード・映像の調整・音ズレ補正・黒い縁の切り取り・低遅延・保存方法をまとめて覚えます。最大9個で、プロファイルメニューか Ctrl+1〜9 で切り替えます。切り替えた後に設定を変えると「変更あり」と表示され、上書きするまでプロファイルは変わりません
- **プロファイルの自動切り替え** — 各プロファイルは、使っていた入力の特徴（キャプチャデバイス・映像モード・絵の本当の細かさ・ゲームのコマ数）を覚えます。保存・上書きしたときと、そのプロファイルで同じ入力を1分ほど使い続けたときに記録します。デバイスをつないだとき、映像モードや解像度が変わったとき、起動して約10秒たったときに、今の入力と比べて、選択中のものより明らかに合うプロファイルがあれば「Switch のプロファイルに切り替えますか？（クリックで切り替え）」と出します。プロファイル → プロファイルの自動切り替えで、オフ／確認する（既定）／自動で切り替える を選べます。設定を触ってから30秒以内、テストモード中、同じ入力の変化では1回しか提案しません。1080p60 の機器が2台あって特徴が同じときなど、見分けられないときは何もしません（記録していないプロファイルは判断の材料になりません）。HDR かどうかや黒い縁は見ていません
- **黒い縁の切り取り** — 映像 → 黒い縁の切り取りで、映像の四辺の黒い縁を数値または「自動で検出」で切り取ります。切り取った絵に合わせて拡大され、スナップショットにも反映されます（Direct3D 描画のとき）
- **表示どおりに保存** — オプション → スナップショット設定で、画面に出ている大きさ（拡大の画質を反映）のままスナップショットを保存できます（Direct3D 描画のとき。一時停止中はソースの大きさで保存します）
- **低遅延モード（試験版）** — 映像 → 低遅延モードで、垂直同期を待たずにフレームを即座に表示します。ティアリングを許可できる環境では、ボーダーレスの全画面でインディペンデントフリップ / VRR（可変リフレッシュレート）を使えます（Direct3D 描画のとき。切り替えると映像が一度つながり直ります）
- **なめらか ⇔ 低遅延** — `Ctrl+Alt+L`（映像メニュー・右クリックメニューにもあります）で、「なめらか」（フレーム補間オン・低遅延オフ）と「低遅延」（低遅延オン。補間は働きません）をワンキーで切り替えます。切り替えると「なめらか（補間 39→144 fps・遅れ 約 50 ms）」「低遅延（遅れ 約 15 ms）」のように現在の様子を出します。映像は一度つながり直りますが、全画面のままです（Direct3D 描画のとき）。キーはオプション → ホットキー設定で変えられます
- **自分専用モデル** — 自分のゲームの絵で学習させた拡大モデルを作って使えます（オプション → 自分専用モデル → 学習用の絵を集める → 学習 → 映像 → 拡大の画質 → 自分専用モデル）。仕組みは「くっきり」と同じなので GPU の使い方も同じです。手順は下の「自分専用モデルを作る」。
- **回転・左右反転**、**デジタルズーム**（Ctrl+ホイール）とドラッグでのパン
- **全画面 / ピクチャインピクチャ**（不透明度・クリックスルー・表示位置・サイズを設定可能）
- **全画面にするモニター** — 表示 → 全画面にするモニターで、全画面にする画面を選べます（既定はウィンドウがあるモニター）。メイン画面で操作しながら、別のテレビ・モニターに映すといった使い方ができます。モニターは機種名で覚えるので、解像度やつなぎ方を変えても同じモニターを使います。選んだモニターが外れているときは、今のモニターで全画面にします。モニターの増減や解像度の変更があったときは、全画面・PiP・ウィンドウの位置を自動で直します
- **ゲーム機の電源に合わせる** — ゲーム機の電源が切れていると、キャプチャカードは自分で黒い「No Signal」画面を出すか、ただ真っ黒な絵を送ってきます。YuCap はそれを見分けて（黒地に少しの文字が 2 秒以上、または全面の黒が 3 秒以上、まったく動かないとき）「信号なし」とし、情報表示やステータスバーに「静止」ではなく「信号なし」と出します。映像が戻って 1.5 秒続くと「信号あり」に変わります（Direct3D 描画のとき）。
  表示 → ゲーム機の電源に合わせる で、「信号が来たとき: 全画面にする」（「全画面にするモニター」に出ます。既定はオフ）と、「信号がなくなったとき: ウィンドウに戻す」（自動で全画面にしたときだけ戻します。既定は「そのまま」）を選べます。動くのは「信号なし → 信号あり」のような変わり目だけで、手で全画面にしたり戻したりした操作とは争いません。起動したときにすでに映像が来ている場合も動きません。
  既定をオフにしているのは、ゲームの真っ黒な画面が 3 秒以上続くときや、暗くて文字だけがある静止した画面（読み込み中など）が、カードの画面と区別できず「信号なし」になることがあるためです。暗くても動いている場面はなりません。
  信号なしが 5 秒以上続くと省電力になり、補間・拡大の画質処理（FSR・くっきり）・「元の細かさに合わせて拡大」・くっきり度の計測を止め、表示を 1 秒に 2 回ほどにします（GPU はほとんど使いません）。映像が戻れば、最初の 1 コマですぐに通常へ戻ります
- **配信用ウィンドウ** — 表示 → 配信用ウィンドウを開く で、映像だけを出す別のウィンドウ（タイトル「YuCap 配信用」）を開きます。OSD・情報表示・メニュー・ステータスバー・カーソルは入らず、背景は黒、大きさは固定（表示 → 配信用ウィンドウの大きさ: 1920x1080（既定）・1280x720・2560x1440・3840x2160・映像と同じ）で、映像は縦横比を保って収めます。開いてもフォーカスを奪いません。拡大の画質・フレーム補間・映像の調整・切り取り・回転は本体と同じに反映されます（くっきり（Anime4K）は FSR、「元の細かさに合わせて拡大」は使いません）。本体の表示のあとに描くので、本体のコマの出方は変わりません（テストモードで確かめます）。開いているかと大きさは覚え、本体を閉じると一緒に閉じます。Direct3D 描画のときに使えます（OBS での使い方は下の「OBS で配信・録画するには」）
- **テストモード（自動試験）** — ヘルプ → テストモードで、実機（キャプチャカード・テレビなど）の動作を自動で一通り試験し、レポートを作ります。全映像モードの取り込みコマ数、GPU の余裕、コマの出方（カクつき）と VRR の効き、全画面での通知の見え方、FSR の比較画像、HDR 入力、各機能、音声、ダイアログの表示崩れを調べます。レポートは「ピクチャ」の `YuCap\テストレポート\（日時）\report.html` に保存され、試験中に変えた設定は終了後に元へ戻ります（Esc で中止）
- **一時停止**（Space）— 映像を静止し音声も停止
- **スナップショット** — **ソース解像度そのまま**保存（ウィンドウが小さくても4K入力なら4Kで保存、他ウィンドウが重なっても影響なし）。PNG/JPEG、クリップボードへコピー、連写（間隔・枚数指定）
- **スナップショット一覧** — ファイル → スナップショット一覧（Ctrl+G）で、保存した画像をサムネイルで新しい順に見られます。大きなプレビュー、フィルター、フォルダごとの表示、コピー・フォルダで表示・開く・名前の変更・削除（ごみ箱へ）に対応し、矢印キー・Enter・Delete・F2・Ctrl+C でも操作できます。数千枚あっても、見えている分だけを読み込むので軽く動きます。保存すると一覧は自動で更新され、保存直後の通知をクリックするとその画像を選んだ状態で開きます
- **保存の設定を増やしました** — オプション → スナップショット設定で、「保存したらクリップボードにもコピーする」と「プロファイルごとにフォルダを分ける」（保存先の中に、使っているプロファイルの名前のフォルダを作って保存）を選べます。どちらも既定はオフです。ファイル名は日付と時刻（ミリ秒まで）で、同時に保存しても重なりません
- **音声パススルー** — 音量 0〜500%（ソフトリミッター内蔵で歪みにくい）、ミュート、遅延の実測表示。音の遅れは小さく（目安は合計 70〜90 ms 前後）、キャプチャカードの音を細かく受け取り、Windows の出力側も最小限の待ちで鳴らします。
  **音声バッファ設定**（音声 → 音声バッファ設定）の「安全のための余裕」は、音を出す前に YuCap がためておく量で、これが YuCap がわざと足している唯一の遅れです。小さいほど音の遅れが減りますが、小さすぎると音が途切れます（既定 40 ms、途切れるときは大きくしてください）。バージョン 1.8 以前の既定値（120 ms / 200 ms）のままだった設定は、初回だけ新しい既定に切り替わります
- **音声の出力先** — デバイス → 音声の出力先で、Windows の既定のほか、好きなスピーカー・ヘッドホンを選べます。選んだ機器が外れたときは Windows の既定に切り替え、戻ると自動で選んだ機器に戻ります
- **グローバルホットキー**（他アプリ使用中でも動作、キー割り当て変更可）
- **カーソル自動非表示**（時間設定可）、**画面スリープ抑止**

## OBS で配信・録画するには

表示 → 配信用ウィンドウを開く で「YuCap 配信用」のウィンドウを開き、OBS からそれを取り込みます（Direct3D 描画のとき）。

1. OBS の「ソース」の ＋ → **ウィンドウキャプチャ** を追加します
2. 「ウィンドウ」で **[YuCap.exe]: YuCap 配信用** を選びます
3. 「キャプチャ方法」を **Windows 10 (1903 以降)** にします。ほかのウィンドウに隠れていても、別のモニターにあっても取り込めます（最小化すると取り込めなくなるので、最小化はしないでください）
4. 「カーソルをキャプチャする」を **オフ** にします
5. 音声は、ソースの ＋ → **アプリケーション音声キャプチャ** を追加し、ウィンドウに YuCap を選びます

OBS の表記はバージョンによって少し違います（アプリケーション音声キャプチャは古い版では見つからないことや、「（ベータ）」と付くことがあります）。見つからないときは、OBS のバージョンを上げるか、音声出力キャプチャ（Windows の出力全体）を使ってください。ウィンドウの大きさは OBS の出力解像度に合わせておくと、拡縮せずにそのまま映ります。

## 自分専用モデルを作る

自分のゲームの絵で学習させた、自分専用の拡大モデルを作って使えます。仕組みは「くっきり」と同じ（Anime4K の M と同じ形のニューラルネット）で、中の数字（重み）だけが自分の絵で学習し直したものです。そのため GPU の使い方も同じで、YuCap 側に新しい処理は増えません。

**流れは「集める → 学習する → 選ぶ」の 3 つです。**

### 1. 集める

オプション → 自分専用モデル → **学習用の絵を集める** をオンにして、いつもどおり遊びます（既定はオフです）。

- ゲームの絵が動いているあいだ、数秒おきに**そのままの大きさ**（拡大前の絵）を PNG で保存します。カードの「No Signal」画面・真っ黒や真っ平らな絵・止まっている絵（ポーズ画面や HUD だけの静止画面）・保存済みと似た絵は保存しません。
- 保存先は `%LOCALAPPDATA%\YuCapTrain\data\<プロファイル名>` です（プロファイルごとに分かれます。使っていないときは `default`）。ステータスバーに「学習用の絵: 1234 枚」と出ます。
- 保存した絵は 1 枚ずつ `index.jsonl` に、絵の大きさと「本当の細かさ」（720p 相当など）の推定が記録されます。学習では、本当に 1080p の細かさがある絵を重く扱います。
- 容量の上限は 5 GB です（`settings.json` の `TrainCapGb` で変えられます）。超えると古い絵から消します。ドライブの空きが 2 GB を切ると止まります。
- 描画（映像の表示）は止めません。保存・判定は別のスレッドで行い、描画スレッドは GPU のコピーを頼むだけです。通信は一切しません。

目安: 学習には**数百〜数千枚、いろいろな場面**がほしいです（街・戦闘・メニュー・暗い場所など）。同じ場面ばかりだと、その場面だけが良くなって、ほかでは変わらないか悪くなります。
数十枚の同じゲームでも学習は動き、検証用の絵では元の Anime4K より少し良くなりますが、絵を 15 枚から 45 枚に増やしても、検証の数字はほとんど変わりませんでした（ネットワークが小さく、同じ場面では頭打ちになるのが早いためです）。差が出やすいのは、別のゲームや、学習で想定していない縮め方の絵に使ったときで、悪くなることもあります。**効いたかどうかは、必ずテストモードの数字（学習に使っていない絵）で確かめてください。**

### 2. 学習する

学習には NVIDIA の GPU と Python 3.10〜3.12 が必要です。最初に 1 回だけ、学習環境を作ります（PyTorch が約 2 GB。YuCap 本体は何も入れず、`%LOCALAPPDATA%\YuCapTrain\venv` の中だけに入ります）。

```bash
powershell -ExecutionPolicy Bypass -File tools\setup_train_env.ps1
```

学習します（`-Minutes` は時間の上限。30 分でも、絵が少なければ早く頭打ちになります）。

```bash
powershell -ExecutionPolicy Bypass -File tools\train_model.ps1 -Name mine -Profile default -Minutes 30
```

学習は「元の Anime4K M の重み」から始めて、自分の絵に合わせて少しずつ直します（30 分で十分です。RTX 4060 で毎秒 30 回ほど更新します）。入力は集めた絵を半分の大きさに縮めたもの（縮め方・色の間引き・ノイズをいろいろ変えて、キャプチャを真似ます）、答えは元の絵です。絵は**場面のまとまりごと**に学習用と検証用に分けるので、検証には学習に使っていない場面だけが使われます。終わると、学習前の Anime4K と自分のモデルを検証用の絵で比べた表（PSNR・SSIM・輪郭の強さ）が出て、`%LOCALAPPDATA%\YuCapTrain\models\mine.hlsl` ができます。**自分のモデルが元の Anime4K を上回らなかったときは、そう表に出ます**（その場合は絵を増やすか、使わないでください）。

### 3. 選ぶ

映像 → 拡大の画質 → **自分専用モデル（mine）** を選びます（作ったモデルがあるときだけ出ます。YuCap を開いたままでも、次にメニューを開いたときに出ます）。「くっきり（アニメ・イラスト向け）」に戻せばいつでも元の Anime4K です。作り直したモデルは、同じ名前で上書きすれば次の絵から使われます（再起動もビルドも不要です）。

数字で確かめたいときは、ヘルプ → テストモード（拡大の項目）が、学習に使っていない絵で FSR・くっきり・自分専用モデルを比べて、SSIM と PSNR のどちらも上回ったときだけ「上回った」と書きます。コマンドラインなら:

```bash
YuCap.exe --a4k-check <出力先> --model mine --frames <画像フォルダ>
```

手持ちの絵（スナップショットなど）で学習したいときは、まず `YuCap.exe --res-estimate-check <出力先> --index <フォルダー>` でそのフォルダーに `index.jsonl`（絵ごとの本当の細かさ）を作ってから、`tools\train_upscaler.py train --data <フォルダー>` に渡します。絵は縮めた 720p 相当でも、1080p のきれいな絵でも使えます（細かさが画面の大きさより小さい絵は、その細かさまで縮めた絵を正解にして学習します）。

### すべて消すには

`%LOCALAPPDATA%\YuCapTrain` フォルダーを削除します（集めた絵・学習環境・モデルがすべて入っています）。YuCap の設定の「自分専用モデル」は、モデルが無くなると自動で「くっきり」に戻ります。

## SmartScreen の警告について

配布している exe にはコード署名を付けていないため、初回実行時に Windows SmartScreen の警告
（「WindowsによってPCが保護されました」）が表示されます。**［詳細情報］→［実行］** で起動できます。

心配な場合は、ダウンロードした exe のハッシュがリリースページ記載の SHA256 と一致するか確認してください。

```powershell
Get-FileHash YuCap.exe -Algorithm SHA256
```

## 外部通信について

YuCap が外部と通信するのは**更新確認のときだけ**です。それ以外の通信は一切行いません
（使用状況の送信などはありません）。

- 通信先: GitHub Releases API（`https://api.github.com/repos/Yu5rin/YuCap/releases/latest`）
- タイミング: 起動のたび（起動を妨げないよう非同期で実行）、またはメニューの「更新を確認」を押したとき
- 通信先URLは `settings.json` の `UpdateApiUrl` に持たせてあり、変更・確認できます
  （接続先は GitHub のホストに限定しています。リリース応答には照合用の SHA256 も
  含まれるため、任意のホストを許すとハッシュ検証が意味を失うためです）
- 自動更新は **オプション → 自動で更新する** でオフにできます（オフにすると確認もダウンロードも行いません）

「自分専用モデル」の学習環境（`tools\setup_train_env.ps1`）が PyTorch などを取ってくるのは、あなたがそのスクリプトを動かしたときだけで、YuCap 本体は通信しません。
学習用の絵を集める処理も、保存はこのパソコンの中だけです。

ダウンロードした実行ファイルは `%LOCALAPPDATA%\YuCap\update` に置き、SHA256 を照合します。
置き換える直前にも、もう一度照合します（食い違えば破棄して何もしません）。
照合用の SHA256 が公開されていない版は自動では入れません。
更新は「現在の exe をリネームして退避 → 新しい exe を配置」という手順で行い、
途中で失敗した場合は退避したものを書き戻します（`Program Files` などの書き込めない場所に
置かれている場合は自動では入れず、通知してリリースページを案内します）。

## 設計メモ（触る前に読む価値のある落とし穴）

- **`UpdateVideo` は必ずワーカースレッドから呼ぶ。** UIスレッドから呼ぶと、MF内部がUIスレッドの応答を
  待つためデッドロックする（全画面化で数秒〜無限に固まる）。戻り値 `S_FALSE (0x1)` は**正常**であり
  失敗ではない。
- **`UpdateVideo` に `dst=NULL`（fill window）を渡してはいけない。** DirectComposition では明示矩形が
  合成ビジュアルのリサイズ契機になっており、NULL だと全画面で何も描画されない。
- **プレビュー描画ストリームに `SetSampleCallback` を設定しない。** フレームがレンダラから奪われ、
  プレビューが真っ白になる。
- **フレーム補間（`Shaders/interp.hlsl`、`D3DRenderer` の `InterpUpdate`）は垂直同期に合わせて動く Direct3D 専用の機能。**
  働く条件は「設定オン・Direct3D・低遅延でない・画面の更新 ≥ 映像のコマ数 × 1.1（一度働いたら × 1.05 まで）」で、
  約 1 秒ごとに描画スレッドが見直す。仕組みは次のとおり。
  - 取り込みスレッドが各コマの到着時刻をなめらかにならした時刻（`Slot.Smooth`、位相ロックループ。到着のばらつきを
    そのまま使うと補間の位置が揺れる）を付ける。働いている間は映像を `ユーザー遅延 + ペーシング余白 + 1 コマ` だけ
    リングに溜め、更新ごとに時刻 T = 今 − その遅延 を求めて、T の直前のコマ A と次のコマ B の間の位置 alpha で絵を作る
    （1 コマぶんの遅延が増えるのはこのため）。
  - A・B を向き変換済みの BGRA とその輝度ピラミッド（1/2〜1/16。2560 画素より広い映像＝4K は 1/4〜1/32 から始め、探索の重さを 1080p と同じにする）にしておき、コマの組が変わったときだけ動き推定を行う
    （次の組では B が A になるので、変換とピラミッドは使い回す）。動き推定は粗い方から細かい方へのブロックマッチングで、
    A(x − v/2) と B(x + v/2) を比べる対称型（4×4 画素ごとに 1 本、8×8 の窓、前の段の動きを候補にして ±1・±0.5 画素で詰め、
    各段の後に 3×3 のメディアンをかける）。
  - 合成は `A(p − alpha·v)` と `B(p + (1 − alpha)·v)` の混ぜ合わせで、2 つが食い違うところ（動きが当たっていない所）は
    近い方のコマをそのまま使う。結果は `_oriented` に書くので、拡大・FSR・スナップショットは今までどおり。
  - 補間が働いていないときの経路（`AdvanceDelayed`）は変えていない。60 fps を 59.94 Hz で見るときのカクつきの対策はそちらに依存する。
- **ゲームの実際のコマ数（情報表示の「（ゲーム 30 fps）」）は、取り込んだコマごとに GPU で「前のコマと同じ絵か」を調べて数える。**
  30 fps で描くゲームを 60 fps で取り込むと、同じ絵が 2 コマずつ届く。`Shaders/dup.hlsl` の計算シェーダー 1 回（0.06 ms 未満）が、
  コマの輝度を 120×68 に縮めた絵（各画素は元の 16×16 ほどの平均）を作り、直前のコマの縮小画像との差を 4 つの数字（差の合計・最大・
  画素数 2 種）にする。数字はステージングバッファ（12 個の輪）へコピーして、次のコマ以降に `Map(DO_NOT_WAIT)` で拾う（待たない。
  拾えるのは取り込み順の先頭から。拾えなければ次の機会に回す）。**しきい値は演算誤差のすぐ上（平均 0.0005・最大 0.08 レベル）にしてある。**
  このカードの 1080p60 は「繰り返しの絵」で差がちょうど 0 になる（ビット単位で同じ）一方、本物のゆっくりした変化（フェードの最初のコマ）は
  平均 0.0006・最大 0.3 レベルあり、各コマは直前のコマとだけ比べる（最後に採用した絵とは比べない）ため、ゆるくするとゆっくりした
  パンが全部「同じ絵」になって絵が進まなくなる。圧縮した形式（Motion-JPEG）では繰り返しでもぴったり同じにならず、すべて新しい絵と
  みなされる（従来どおりの動きになるだけで安全）。1 秒ぶんのコマのうち新しい絵の数をコマの受信速度に掛けたものがゲームのコマ数で、
  1 秒に新しい絵が 1 つ以下なら「静止」（0 fps とは表示しない）。
- **新しい絵だけの補間（`PairSelect`・`UniqueTimeline`）。** 繰り返しのコマがあると、従来の補間は「同じ絵と同じ絵」の組（動きが止まる）の
  次に「違う絵」との組（一気に進む）を作り、補間していてもカクつく。判定が付いたコマはリングの中で「繰り返し」の印を付け、A と B は
  繰り返しを飛ばして選ぶ。新しい絵の時刻は、繰り返しがあるとき（絵の間隔が 1.3 コマ以上）だけ、新しい絵の間隔に対する位相ロック
  （直近 12 枚の平均間隔、ゲイン 0.15）で均等に並べる（40 fps＝1,2,1,2 コマおきでも 25 ms おきに揃う）。繰り返しがなければ時刻は従来と同じ。
  判定は数コマ遅れて届くため、判定の前のコマは「新しい絵」として扱う（従来の動き）。**保持する時間は、新しい絵 1 つ分の間隔と、判定が届くまでの
  最大の遅れ、時刻を均した分の遅れの合計だけ増える**（30 fps のゲームで約 +50 ms。上がるときは更新ごとに半分の速さで、下がるときは
  0.1 ms ずつ）。ゲームが映像と同じコマ数なら増えない。確認は `--interp-seq-eval`（実際の連続コマの再生）とテストモードの
  「ゲームのコマ数に合わせた補間」。
- **リフレッシュレートの違うモニターを並べているとき（例: メイン 60 Hz・サブ 144 Hz）、サブの画面の映像の上に何かが重なっていると、
  その間 Windows はサブの画面も約 60 Hz でしか書き換えない。** 映像だけが画面に出ているときは 144 Hz で表示される。
  通知・情報表示・一時停止の画像・ほかのウィンドウが映像に重なっている間がこれに当たり、アプリの中からは避けられない
  （ウィンドウのスワップチェーンでも同じ）。テストモードは測定の間だけ見出しを隠す。
  表示のタイミングは映像のあるモニターの `IDXGIOutput::WaitForVBlank` に合わせる（`VBlankBeat.cs`）。
  `D3DKMTWaitForVerticalBlankEvent` はこの構成でサブのモニターでもメインの間隔を返すため使わない（`--vblank-probe` で確かめられる）。
- **Windows の HDR がオンのモニターでは、8bit（B8G8R8A8）の合成スワップチェーンはメインの更新（約 60 Hz）に抑えられる。** メイン 59.94 Hz の SDR・
  サブ 144 Hz の HDR オンのテレビで、何も重ねなくても B8G8R8A8 の合成スワップチェーンは 60 fps、R10G10B10A2（色空間は SDR のまま、または HDR10）・
  R16G16B16A16_FLOAT（scRGB）は 144 fps（`--vblank-probe` の `composition,hdr10` / `composition,scrgb` / `composition,rgb10sdr`）。
  そこで、HDR 表示がオフでも、そのモニターが Windows の HDR のときは 10bit（R10G10B10A2・sRGB）のスワップチェーンに切り替える（`D3DRenderer.Nv.cs` の
  `HdrUpdate` / `SetSwapMode(1)`）。絵の値は変えず、Windows が他の SDR のウィンドウと同じ「SDR コンテンツの明るさ」に置き直すので見た目は同じ。
  HDR のないモニター（メインなど）へ動かすと 8bit に戻る（モニターの状態は 1 秒ごとに別スレッドで調べる）。静止画は SDR のまま。
- **通知・情報表示・テストの見出しは、Direct3D 描画では映像の中（スワップチェーン）に描く。** 映像の上に子ウィンドウを
  重ねると Windows は直接表示（direct flip）をやめて合成するため、上の段落のとおりサブのモニターが 144 Hz から約 60 Hz に
  落ちる。そこで `OsdOverlay` / `InfoOverlay` / `TestCaption`（`OverlayControl`）は配置・状態・描画コードをそのまま持ちつつ、
  Direct3D のときはウィンドウとして表示せず、変化したときだけ（毎フレームではなく）白と黒の2枚の上に描いて
  アルファを復元した premultiplied BGRA にし、`IVideoEngine.SetOverlays` で描画スレッドに渡す。描画スレッドは
  バックバッファへの描画の最後（スナップショット用の `_lastComposed` へのコピーより後）にアルファ合成するので、
  保存した画像には写らない。通知のクリックは、ウィンドウが無いためキャンバスのクリックで矩形判定して処理する。
  一時停止中は一時停止の画像（ウィンドウ）が映像の上に出るため、通知・情報表示は一時的にウィンドウに戻す。
  Media Foundation 描画は従来どおり子ウィンドウ。
- **くっきり度（状態バー・情報表示）は、約 5 秒ごとに出力の 512×512 だけを「今の拡大処理」と「ふつうの拡大（バイリニア）」で
  画面外に描いて比べる。** 描画スレッドでは 2 回の描画とステージングへのコピーを投げるだけで、読み出しは数十 ms 後に
  別の要求で行い、輪郭の強さ（テストモードの FSR 比較と同じ指標）は別スレッドで計算する。1 回あたりの描画スレッドの
  占有はログ（`crispness sample`）とテストモードで確認できる。

- 万一 `UpdateVideo` が固着した場合に備え、セッションを分離し、検知したらプレビューを自動再起動する
  仕組みを入れている（`--selftest` で両方の経路を検証できる）。

- **音声の遅れの内訳と、遅れが大きかった理由。** 音の遅れは「カードの区切り（取り込みの間隔）＋ YuCap の余裕 ＋ 出力デバイスの待ち」。
  以前は NAudio の `WasapiCapture` が既定の「一定間隔で見に行く」方式（バッファ 100 ms）で、カードの音が約 62 ms ごとのかたまりで届き
  （`--audio-probe ... --poll --capbuf 100` で再現できる）、出力の `WasapiOut` はバッファ全体を毎回満たすため出力側に余裕と同じ長さ（200 ms ＋丸め）の待ちができていた。
  今は取り込みをイベント駆動・20 ms バッファにして 10 ms ごとに受け取り（カード側の区切りも 10 ms）、出力は `AudioRender.cs` の自前ループで
  エンジンの周期（IAudioClient3、通常 10 ms）に合わせて 2 周期ぶん（約 20 ms）だけ溜める。1 周期では出力側が空になって途切れる（`--periods 1`）。
  余裕のバッファは、無音を足して `余裕＋A/V同期の遅れ` に保ち（足りなくなったら補充）、溜まりすぎたら古い側から捨てる。
- **音声の「余裕」の既定値は実測で決めた。** 取り込みが 10 ms 間隔なら 20 ms でも 20 秒間に途切れなし（CPU を全コア飽和させても同じ）。
  カードや環境の揺れに備えて既定は 40 ms。

## 診断

問題が起きた場合は `%APPDATA%\YuCap\yucap.log`（動作ログ）と `error.log`（クラッシュ）を確認してください。
UIスレッドが固まった場合も、別スレッドの監視により `*** UI THREAD STUCK` として記録されます。
